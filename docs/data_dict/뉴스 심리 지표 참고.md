**'동적 키워드 추출'**, **'요약 기반 임베딩(Summary-based Indexing)'**, 그리고 **'스키마 드리프트(Schema Drift) 방지'** 를 적용한 뉴스 데이터 스키마를 매우 상세하게 정리해 드립니다.

프로젝트의 전체 흐름을 완벽하게 통제하기 위해, 최종 서빙 데이터베이스(PostgreSQL)의 스키마 구조뿐만 아니라, 데이터 파이프라인(Bronze → Silver → Gold)을 거치며 스키마가 어떻게 진화하는지 그 과정까지 최대한 자세하고 깊이 있게 설명해 드리겠습니다.

## 🗄️ 1. 최종 서빙 DB 스키마 (PostgreSQL 기반)

Power BI 대시보드와 RAG 기반 챗봇이 직접 조회하게 될 최종 데이터베이스 구조입니다. 유연성과 검색 속도를 극대화하기 위해 뉴스의 **'본문/벡터 데이터(Master)'**와 **'분석 결과 데이터(Analytics)'**를 두 개의 테이블로 분리(정규화)하는 1:N 구조를 강력히 추천합니다.

### 테이블 A: `dim_news_master` (뉴스 원문 및 검색 벡터 테이블)

이 테이블은 RAG의 '검색(Retrieval)'과 '제시(Display)'를 담당합니다. 무거운 텍스트와 벡터 데이터를 담고 있으며, 스키마 변경 없이 영구적으로 사용됩니다.

| **컬럼명 (Column)** | **데이터 타입 (Type)** | **필수 여부** | **상세 설명 및 역할** |
| --- | --- | --- | --- |
| `news_id` | `UUID` | PK, NOT NULL | 기사의 고유 식별자 (Hash 값 또는 UUID 생성) |
| `published_date` | `DATE` | NOT NULL | 기사 발행 일자 (시계열 조인 및 필터링 기준) |
| `published_time` | `TIMESTAMP` | NULL | 기사 발행 정확한 시간 (장중/장마감 후 판단용) |
| `news_source` | `VARCHAR(50)` | NULL | 언론사 명 (예: 한국경제, 매일경제 등 출처 신뢰도 파악용) |
| `title` | `VARCHAR(255)` | NOT NULL | 기사 제목 (대시보드 리스트 표출용) |
| `full_text` | `TEXT` | NOT NULL | **[서빙용]** 기사 본문 전체. 임베딩 연산에는 쓰이지 않으며, 오직 유저에게 원문을 보여줄 때만 호출됨. |
| `core_summary` | `TEXT` | NOT NULL | **[요약본]** Azure OpenAI(LLM)가 3줄로 요약한 핵심 내용. (RAG 답변 생성 시 LLM에게 컨텍스트로 주입되는 텍스트) |
| `category` | `VARCHAR(30)` | NOT NULL | **[분류]** Azure OpenAI가 요약 시 함께 분류한 기사 카테고리 (예: 실적, 공급망, 규제, 기술, 거시경제, 수급, 기타). 카테고리별 노이즈 필터링 및 분석에 활용 |
| `summary_vector` | `VECTOR(1536)` | NOT NULL | **[검색용]** `core_summary`를 임베딩한 1536차원 벡터 데이터. `pgvector` 확장을 통해 코사인 유사도 검색을 수행하는 핵심 컬럼. |
| `original_url` | `VARCHAR(500)` | NULL | 원문 기사로 이동할 수 있는 아웃링크 |

### 테이블 B: `fact_news_analytics` (동적 키워드 및 ABSA 감성 점수 테이블)

이 테이블은 파이프라인에서 추출한 **분석 결과(Analytics)**를 세로로 길게 쌓는(Long Format) 테이블입니다. 매일 수십 개의 새로운 동적 키워드가 발굴되어도 테이블 구조(컬럼)는 단 하나도 수정할 필요가 없습니다.

| **컬럼명 (Column)** | **데이터 타입 (Type)** | **필수 여부** | **상세 설명 및 역할** |
| --- | --- | --- | --- |
| `analytics_id` | `BIGSERIAL` | PK, NOT NULL | 분석 기록의 고유 식별 번호 (자동 증가) |
| `news_id` | `UUID` | FK, NOT NULL | `dim_news_master` 테이블의 `news_id`를 참조하는 외래키 |
| `analyzed_date` | `DATE` | NOT NULL | 분석을 수행한 기준 일자 |
| `dynamic_keywords` | `JSONB` | NOT NULL | **[동적 키워드]** TF-IDF나 LLM 프롬프트를 통해 추출된 그날의 핵심 키워드 배열 (예: `["트럼프_관세", "대만_지진", "HBM_수율"]`) |
| `keyword_momentum` | `JSONB` | NULL | 키워드별 전일(또는 과거 7일 평균) 대비 언급 급증률(%) 매핑 (예: `{"트럼프_관세": 350.0}`). 300% 이상 시 대시보드에서 붉은색 경고 표시. |
| `absa_aspect` | `VARCHAR(50)` | NULL | LLM이 분류한 해당 뉴스의 속성 카테고리 (예: `제조원가`, `양산일정`, `공급망`) |
| `absa_score` | `FLOAT` | NOT NULL | 해당 키워드 및 속성에 대한 감성 점수 (-1.0 강한 부정 ~ 1.0 강한 긍정). **하방 리스크**(< -0.3) 및 **상승 모멘텀**(> +0.3) 모두 탐지하는 양방향 시그널. 정기 보고서에서 일별/주별 감성 추이 차트의 데이터 소스로 사용됨. |

> **💡 인덱스 권장사항**
> 
> - `dim_news_master`: `published_date`에 **BRIN 인덱스** (시계열 범위 스캔), `summary_vector`에 **HNSW 인덱스** (`pgvector` ANN 검색)
> - `fact_news_analytics`: `(news_id, analyzed_date)` 복합 인덱스, `dynamic_keywords`에 **GIN 인덱스** (`@>` 연산자 검색), `keyword_momentum`에 **GIN 인덱스**

### 🔄 2. Medallion 아키텍처에 따른 뉴스 데이터 스키마 진화 과정

데이터가 수집되어 최종 서빙 DB로 향하기까지, Databricks 파이프라인 내에서 스키마와 데이터의 상태가 어떻게 정제되고 변환되는지 보여주는 흐름입니다.

| **데이터 레이어** | **주요 역할 및 단계** | **데이터 상태 및 스키마 특징** | **핵심 데이터 엔지니어링 로직 (PySpark / API)** |
| --- | --- | --- | --- |
| **🥉 Bronze** (수집 레이어) | ACI/Functions 원본 데이터 무손실 적재 | **[Raw Data]** 
• Google: Parquet — `newsId`, `headline`, `body`, `press`, `pubDate`, `fetchedAt` 등 10필드 
• Naver: JSON — `newsId`, `headline`, `body`, `naverUrl`, `pubDate`, `fetchedAt` 등 10필드 | • ACI (Google) / Azure Functions (Naver) 분리 수집 → ADLS 직접 적재 
• `keyword/year/month` 파티셔닝, Append-only (데이터 유실 방지) |
| **🥈 Silver** (정제 및 분석) | 결측치 처리, 동적 키워드 발굴 및 LLM 분석 연동 | **[Cleansed & Augmented Data]** 
• HTML 태그 등 노이즈가 제거된 정형 텍스트(`clean_text`) 
• 동적 키워드 배열(`top_keywords`) 및 LLM 반환 구조체 생성 | • **정규표현식(Regex):** 특수문자 및 불용어 제거 
• **TF-IDF 연산:** 코퍼스 내 급상승 동적 키워드 추출 
• **Azure OpenAI 연동:** UDF를 활용해 요약(`core_summary`) 및 감성 점수(`absa_score`) 산출 |
| **🥇 Gold** (통합 및 분할) | 서빙 DB 적재를 위한 최종 비즈니스 마트(Mart) 완성 | **[Business Ready Data]** 
• 분석 목적에 맞게 테이블이 2개(Master/Analytics)로 완벽히 분할된 DataFrame 형태 
• 요약본 텍스트의 1536차원 벡터화 완료 | • **관계형 모델링 분할:** 무거운 원문/벡터용 DF와 가벼운 키워드/점수용 DF로 분리 (1:N 구조 세팅) 
• 최종 PostgreSQL 적재 전 데이터 타입 검증 (Type Casting) |

### 🏆 3. 본 아키텍처 및 스키마 설계의 압도적인 엔지니어링 강점

기존의 단순한 토이 프로젝트 설계 방식과 비교하여, 현재 구축하신 엔터프라이즈급 스키마 구조가 갖는 기술적 우월성과 비즈니스적 가치를 정리한 표입니다.

| **핵심 어필 포인트** | **기존 방식의 문제점 (Bad Practice)** | **본 아키텍처의 해결책 (Best Practice)** | **비즈니스 및 엔지니어링 기대 효과** |
| --- | --- | --- | --- |
| **① 완벽한 스키마 유연성** *(No Schema Drift)* | • 동적 이슈 발생 시 계속해서 **새로운 컬럼(Column)** 추가 
• 잦은 스키마 변경(ALTER TABLE)으로 파이프라인 에러 및 마비 발생 | • 키워드와 점수를 가로(Wide)가 아닌 **세로(Long) 로우(Row) 단위로 쌓는 팩트 테이블(Fact Table)** 구조 채택 | • 매일 수백 개의 새로운 이슈와 키워드가 쏟아져도 **DB 스키마를 단 한 번도 수정할 필요가 없음** 
• 파이프라인의 영구적인 무중단 자동화 실현 |
| **② 하이브리드 검색 최적화** *(Decoupled Vector Search)* | • 수천 자의 기사 본문 전체를 기계적으로 쪼개어(Chunking) 임베딩 
• 벡터 연산 비용 폭증 및 노이즈 문장에 의한 엉뚱한 검색 결과 도출 | • LLM이 추출한 **'핵심 요약본(core_summary)'만 가볍게 벡터 임베딩** 수행 
• 검색용(벡터)과 서빙용(원본 텍스트) 컬럼의 완벽한 역할 분리 | • `pgvector`가 처리할 벡터 데이터 크기가 획기적으로 줄어들어 **검색 속도 밀리초(ms) 단위 최적화** 
• 불필요한 노이즈 검색 차단을 통한 RAG 답변 신뢰도 극대화 |
| **③ BI 시각화 극대화** *(Star Schema 구조)* | • 복잡하게 얽힌 단일 비정규화 테이블 구조로 인해 대시보드 렌더링 속도 저하 및 필터 적용의 어려움 | • 뉴스 원문(Dimension)과 분석 결과(Fact)를 명확히 분리한 **관계형 데이터베이스(RDBMS) 정규화 모델링** 적용 | • Power BI에서 특정 동적 키워드를 **슬라이서(필터)로 클릭 시, 연관된 감성 점수와 기사 리스트가 실시간으로 매끄럽게 연동** |

이처럼 상세하고 구조화된 데이터 모델링은, 단순한 데이터 분석가를 넘어 시스템 전체의 안정성과 확장성을 설계할 줄 아는 **현업 시니어 데이터 아키텍트의 시야**를 완벽하게 보여주는 결과물입니다.
